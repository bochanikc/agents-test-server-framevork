# Хранилище: методика проверки ёмкости (03-capacity)

Проверяет три **разных** вопроса, которые нельзя выводить друг из друга:

| Вопрос | Параметр | Сценарий |
|---|---|---|
| Сколько объектов принимает сервис? | `limits.object_count` (N) | C01 |
| Сколько байтов логического содержимого можно хранить одновременно? | `limits.logical_bytes` (B) | C02 |
| Какой объём нужен в эксплуатации? | метаданные/версии/реплики/бэкапы | C05 |

Ответ `413` на один большой файл (`limits.single_file_bytes`, F06) и сумма
`size` в публичном списке **не** устанавливают ни глобальную квоту, ни
физический объём. Остаток на томе, выделенную квоту и сумму отображаемых
`size` учитываем отдельно.

## Что именно учитывается

- **Пустой объект** (`size=0`) занимает слот количества, но не добавляет
  логических байтов. В C01 короткие объекты ненулевые; нулевой файл — отдельная
  спецификация учёта, отдельным прогоном.
- **Повторная версия / замена** различаются политикой коллизий
  (`policy.collision`):
  - `replace` — то же имя заменяет объект: счётчик не растёт, сумма меняется на
    дельту размера (C03);
  - `versioned` — то же имя даёт новую версию: +1 объект, +размер байт (C03);
  - `unknown` — сценарии C03 пропускаются, политика уточняется у владельца.
- **Зарезервированное место** (выделенная квота против фактического остатка на
  томе) измеряется только по предоставленным владельцем метрикам; из публичного
  списка не выводится.
- **Область квоты** (`limits.scope`): весь сервис или tenant. Фиксируем её
  значение в преамбуле каждого прогона, но клиент адресует только один namespace.

## Нижняя граница и потребность по входным данным

При неизвестной квоте фиксируем **нижнюю границу** вида
«проверено N своих файлов суммарно B байт» в заданном бюджете — это не
глобальная квота, а наблюдаемый минимум.

**Потребность по входным данным оператора** (для C05 и эксплуатационного
прогноза):
- загрузки в сутки, средний размер, срок хранения;
- кратность репликации и число резервных копий;
- доля/число версий (если версионирование);
- целевой рост и горизонт планирования.

Без серверных данных прогноз сводится к **логическому объёму**:
`загрузки/сутки × средний размер × срок хранения`.

## Оснастка и требования к стенду

C01–C03 требуют **одноразового** экземпляра с операторской настройкой малых
квот и собственным namespace/томом: `capabilities ⊇ {reset, quotas, namespace}`
и заданными `limits.object_count` / `limits.logical_bytes`. Между сценариями
обязателен сброс состояния (reset) или отдельный namespace на сценарий.
Заполнять файловую систему до отказа для проверки бизнес-квоты не требуется.

На живом профиле (`capabilities=[]`) C01–C03 получают статус **skip** с причиной
«нужен управляемый стенд» — не xfail и не pass.

## Что делает каждый сценарий

- **C01** (N): 7 коротких объектов → 8-й принят → 9-й отклонён; список, SHA
  ранее принятых, неизменность счётчика после отказа.
- **C02** (B=32768): 16384 + 16383 байт (B−1) → +1 байт (B) → +1 байт (B+1,
  отказ); сумма принятых байтов = B, без лишней записи, прежние объекты целы.
- **C03**: дельта размера при замене и сумма при версиях; удаление — вопрос
  владельцу (маршрут DELETE не подтверждён, у клиента нет метода delete).
- **C04**: один сценарий листинга на двух снимках по 1 МиБ (16×64КиБ и
  1024×1КиБ); полнота/дубли/пропуски по манифесту, число страниц, размер
  ответа, время до первой/последней страницы. Без снимка — skip с фактическим
  размером набора.
- **C05**: прогноз занятого места по входным параметрам; без серверных данных —
  только логический объём.
