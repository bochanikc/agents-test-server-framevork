Готовность файлового сервиса к релизу

24–25 ноября 2026 г. · общий учебный стенд · проверка через публичный HTTP API · версия сборки неизвестна

Итог

NO-GO. Рекомендую отложить релиз. Клиент может получить подтверждение загрузки новой редакции и передать получателю ссылку, которая откроет старый документ. Под нагрузкой сервис также переставал обслуживать запросы. Оба риска затрагивают основное назначение сервиса — сохранить файл и отдать нужные байты по ссылке.

Для проверки я проходил путь отправителя и получателя, сравнивал размер и SHA-256, проверял ошибки ввода и наблюдал за каталогом и доступностью. Фреймворк на Python и сценарии k6 приложены вместе с выборкой измерений. Git-репозиторий · Технический отчёт

Что работает

  • Файл с уникальным именем прошёл полный цикл. На контрольном примере 124 байта и SHA-256 после скачивания совпали с исходными. Пустой файл сохранился с размером 0.
  • Отсутствующий файл вернул 404, форма без файла — 400. Файл в 1 МиБ принят, на один байт больше — 413. Пакет из двух файлов по 600 КиБ принят. Граница в 1 МиБ в этих примерах относится к отдельному файлу.
  • Один полный запрос каталога вернул корректный JSON с 79 710 записями. Ответ занял 44,83 с и 14,72 МБ. Это успешное чтение, но пользователю пришлось ждать почти 45 секунд.

Проблемы

Риск Что наблюдалось Что это значит для пользователя
F04 · High. Повторное имя Первичные материалы показывают старую редакцию на 2 из 6 имён. В одном примере квитанция на 14 байт получила тот же URL, по которому трижды пришли 12 байт с хешем первой редакции. Получатель может открыть устаревший документ даже после успешной загрузки.
AV01 · Critical для испытанного профиля. Потеря доступности В историческом прогоне с пиком 80 виртуальных клиентов k6 зарегистрировал 243 неуспешных запроса из 244. После нагрузки отдельные проверки доступности завершились таймаутом. Клиент может остаться без результата операции. Момент восстановления и длительность непрерывного простоя установить не удалось.

Последнее наблюдение, 25 ноября. Два одновременных чтения каталога завершились сбросом соединения примерно через 153 с каждое. Проверка доступности вернула 200 перед ними и после них. Поэтому для приёмки нужен полный ответ каталога. Этот опыт сам по себе не устанавливает ни предельную параллельность, ни причину предыдущего инцидента. Запись измерения

Другие находки, важные для релиза

Наблюдение Последствие и решение
QA-03 · Ошибка 413 указывает неверный предел. Сообщение говорит о размере всего запроса, хотя пакет из двух файлов по 600 КиБ проходит. Ошибка 413 приходит текстом, а ошибки 400 и 404 для файлов — в JSON. Клиент может предложить пользователю уменьшить весь пакет или потерять объяснение при разборе JSON. В ответе нужно назвать ограничение на один файл и согласовать формат ошибок.
QA-02 · Теряется исходное имя. В проверенном имени «отчёт » превратилось в шесть подчёркиваний. Содержимое сохранилось. Получателю трудно узнать документ. Нужны правило отображения и проверка, что два разных исходных имени можно различить после обработки.
F1/F2 · Анонимный доступ и внутренний путь. По данным ранней проверки, клиент без входа мог загрузить файл, получить каталог и скачать свой тестовый объект. Каталог и квитанция содержали путь хранилища. Для частных вложений это существенный риск. Владелец должен определить права на просмотр списка и чтение, разработка — проверить, нужен ли внутренний путь клиентам. Чтение приватного файла другого пользователя не установлено.
F3 · Клиент видит детали парсера. В ответе 400 на некорректную форму присутствовали фрагмент исключения и служебное значение multipart. Пользователю нужна понятная причина отказа. Технические подробности полезны эксплуатации в журнале запроса.
F6/F7 · Тип и имя скачиваемого файла. Сервис принимал тип, указанный клиентом, и двойное расширение. В проверенных ответах файл выдавался вложением, заголовок nosniff отсутствовал. Для браузерного клиента нужно согласовать типы файлов, заголовки скачивания и требования к HTTPS на релизном входе. Эффект в браузерном предпросмотре не проверялся.

Отдельный диагностический результат за 24 ноября — в пяти интервалах, когда клиент macOS исчерпал 15 секунд ожидания, Linux получил ответ от проверки доступности примерно за 0,11 с. Вопросы

  1. Что именно обещает квитанция при повторном имени? Как получатель выбирает редакцию и что происходит с ранее выданной ссылкой?
  2. Кто вправе увидеть список, прочитать файл и удалить его? Как долго хранится файл и какие ограничения действуют на число объектов и суммарные байты?
  3. Для какого размера каталога, числа пользователей и времени ответа предназначен сервис? Какую пользовательскую операцию считаем признаком восстановления и с какого момента ведём отсчёт?

Что я бы сделал дальше

  1. С владельцем API согласовал бы поведение при совпадении имён. На исправленной сборке проверил бы несколько пар редакций и сопоставил каждую квитанцию, ссылку и скачанные байты с выбранным правилом.
  2. С эксплуатацией сопоставил бы время отказов с журналами прокси и приложения, состоянием хранилища и историей перезапусков. Это помогло бы локализовать сбой и сузить интервал восстановления.
  3. С разработкой и владельцем продукта сверил бы доступ для каждой роли, поведение имён, сообщения об ошибках и заголовки выдачи с утверждённым контрактом.
  4. На управляемой копии проверил бы целевой объём каталога, квоты и восстановление. Релизное решение пересмотрел бы, когда на одной идентифицированной сборке ссылки выдают ожидаемые редакции, каталог возвращает полный JSON в согласованное время, а пользователь после сбоя снова может загрузить и скачать контрольный файл.
